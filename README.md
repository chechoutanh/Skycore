# 🔭 SkyScore: a multi-objective observing-window planner

SkyScore answers one practical question every astronomy club asks: **"When tonight should we point the telescope at this target?"**
It combines celestial mechanics (Astropy), live weather forecasts (Open-Meteo), a machine-learning estimate of atmospheric *seeing*, and a transparent multi-objective scoring function, then presents the result in a Streamlit dashboard.

## Pipeline

```
Astropy ephemeris ─┐
                   ├─► per-hour table ─► normalization ─► weighted score S ─► best window
Open-Meteo API ────┤                         ▲                    │
                   └─► features ─► Random Forest (seeing)         └─► Pareto front, weight-sensitivity
```

## Mathematical model

Each hour $t$ gets four criteria, each mapped to a *goodness* $g_i \in [0,1]$ (1 = best):

| Criterion | Definition |
|---|---|
| Altitude | $g_{\text{alt}} = \max(0, \sin h)$, where $h$ is the target altitude (a proxy for $1/\text{airmass}$) |
| Moon | $g_{\text{moon}} = 1 - k\,\mathbb{1}[h_{\text{moon}}>0]\,(0.4 + 0.6\,e^{-\theta/40^\circ})$, with illuminated fraction $k$ and Moon–target separation $\theta$ |
| Cloud | $g_{\text{cloud}} = 1 - c/100$, with cloud cover $c$ in % |
| Seeing | $g_{\text{see}} = 1 - \operatorname{clip}\!\left(\dfrac{\sigma - 0.8}{3.5 - 0.8},\,0,\,1\right)$, with seeing $\sigma$ in arcsec |

Min-max normalization puts degrees, percentages and arcseconds on a common $[0,1]$ scale. The score is

$$
S(t) \;=\; \mathbb{1}\!\left[\text{observable}(t)\right]\sum_{i} w_i\, g_i(t), \qquad \sum_i w_i = 1,\; w_i \ge 0,
$$

with hard constraints: Sun altitude $< -18^\circ$ (astronomical night) and target altitude $> 15^\circ$.

This is equivalent to the penalty form $S = w_1 A - w_2 M - w_3 C + \text{const}$, written so that every term is "higher is better".

**Extra analysis (beyond a single weighted sum):**

* **Best window:** the contiguous $L$-hour window maximizing the mean of $S$.
* **Pareto front:** hours not dominated in all four criteria simultaneously, so the user can see trade-offs without choosing weights.
* **Weight sensitivity:** weights are drawn from $\mathrm{Dirichlet}(1,1,1,1)$ ($n=500$); we report how often each hour wins. A high win-frequency means the recommendation is robust to the subjective choice of $w$.

## Seeing model (machine learning)

Seeing is driven mostly by upper-level turbulence (jet stream), ground wind and thermal change. Features: 250 hPa wind speed, 10 m wind, $|\Delta T_{3h}|$, $|\Delta p_{3h}|$, dew-point spread, humidity, cloud cover. Model: Random Forest regressor, validated with **time-ordered** `TimeSeriesSplit` (no look-ahead leakage).

### ⚠️ Data honesty

Long-term *measured* seeing archives for a specific site are not freely available. The repository therefore trains on **proxy labels** generated by a physics-inspired formula on synthetic weather (`seeing_model.proxy_seeing`).

| Metric (5-fold time-series CV) | Value |
|---|---|
| MAE | 0.17″ |
| R² | 0.96 |

These numbers only show that the pipeline can recover the proxy; they are **not** evidence of real-world forecasting skill. The default feature importance (250 hPa wind ≈ 0.88) reflects the proxy's construction.

**To make the model scientifically meaningful**, replace the labels with real measurements, for example the club's own observing logs (estimated seeing from double-star splitting or star FWHM in images), merged with archived weather for the same hours, and call `SeeingModel.fit(X, y, label_source="club logs")`. With real labels, report the CV error against a persistence/climatology baseline.

## Quick start

```bash
pip install -r requirements.txt
pytest                      # unit tests
streamlit run app.py        # dashboard
```

Tick **"Offline demo"** in the sidebar if there is no internet; synthetic weather is then used and clearly labeled in the UI.

## Limitations and roadmap

* Light pollution (Bortle class) is not modeled yet; a site-specific constant or a VIIRS-based term could be added as a fifth criterion.
* Solar-system targets use Astropy's built-in ephemeris (accurate to a few arcminutes, fine for planning).
* Next steps: real seeing labels, calibration against actual club sessions, and a baseline comparison.
